### 1c. What "active-slice adoption" actually means

Not "import a rich in-flight slice record" — neither repo has one to import. Concretely it is:

  already-written `docs/adr/0006-phase0-no-go-stop.md` as its artifact, take the `adr_review` gate,

  *adopts* edge-scanner and *drives real work through v2 end-to-end* (§5).
- **sdlc-skills:** nothing — no slice is in flight (`dev-state.md`: "None — `main` is clean at the S3a
  ship").

Historical slices are **not** backfilled. That is the "history stays as written" principle applied
(same guard S3a used: "NOT a migration of already-recorded events — history stays as written").

### 1d. Code or procedure?

`cli/README.md` §"Not in this slice" already names it as a planned command:

> `house archive`, `house adopt`, blocking hooks / `PreToolUse` deny, atomic (tmp+rename) writes, and the
> desktop IDE all land in later slices.

**Recommendation: documented procedure, not a command — with one narrow exception considered and
rejected.**

- Of the four adoption steps, only step 2 (dev-state marker wrap) is mechanical enough to automate,
  and its N is **1** (sdlc-skills already has markers; edge-scanner needs one edit). Writing a command
  + tests to run once is the definition of gold-plating.
- Steps 1 and 3 are `house init` and `git add`. Step 4 is irreducibly judgment — deciding *what*
  in-flight work deserves a slice id and at what tier is a shaper's call, not a parser's.
- A `house adopt` that is `init` + a marker-wrap is a **worse** affordance than telling the truth:
  it implies the migration is push-button when the hard part (step 4) isn't.
- **But S3b must close the loop on the promise**: either build it, or amend `cli/README.md` to say
  adoption is a documented procedure and drop `house adopt` from the "later slices" list. Leaving a
  named-but-never-built command in the README is the drift class this kernel exists to refuse.

Suggested landing: an "Adopting an existing repo" section in `cli/README.md` (~20 lines), plus the
`house init` idempotency already in place. **Est. cost: ~0.15 session.** A `house adopt` command would
be ~40 lines + 4 tests ≈ 0.4 session for N=1 — not worth it now; revisit at the third repo.

```

**Symlinks** (default; `./install.sh copy` copies instead). Current `~/.claude/skills/`:

```

(all six created 2026-07-28; plus 11 unrelated non-house skills)

**⚠ `install.sh` has no prune step.** It only creates. After `git mv skills/house2-shaper

machine. **S3b must either add a prune to `install.sh`** (remove any symlink under `$SKILLS_DST`
whose target is inside `$SKILLS_SRC` and no longer exists) **or ship an explicit `rm` step in the
cutover procedure.** The prune is ~6 lines and is the better answer — it also cleans up after the v1
archive (§3) in the same pass. This is the highest-value non-obvious finding in the sweep.

### 3c. ⚠ `skills/archive/` does not work

`install.sh` globs `"$SKILLS_SRC"/*/`. Moving v1 to `skills/archive/house-shaper/` makes

**Archive destination must be outside `skills/`.** Options, in preference order:

1. **`archive/skills-v1/`** at repo root (or `docs/archive/skills-v1/`) + a `README.md` in it stating

## 4. The name-collision hazard

After the rename, `house-orchestrator` (v2) occupies the v1 name at the same
`~/.claude/skills/house-orchestrator` path.

**What actually breaks:**

1. **Dangling symlinks** (§2d) — the concrete, certain failure. Three `house2-*` links pointing
   nowhere, and if v1 is archived rather than renamed-over, potentially three `house-*` links too.
   Both fixed by an `install.sh` prune.
2. **A session with a cached skill list** — any Claude Code session open across the cutover holds the
   old skill roster and the old `SKILL.md` bodies in context. It may invoke `house2-orchestrator`
   (now gone → dangling link) or invoke `house-orchestrator` **expecting v1 semantics and getting v2**
   — which is the genuinely dangerous case, because v2 refuses to run outside a `.house/` repo and
   drives a completely different loop. A v1-era session in a v1-era repo that reaches for
   `house-orchestrator` after the cutover gets a skill that refuses.
3. **~15 other repos on this machine are still on v1.** ADR-0004's whole rationale: "rewriting
   `house-shaper` in place would swap the process out from under ~15 repos the moment the file is
   saved." **The rename does exactly that** — deliberately, at cutover, which is the point. But it
   means: **the day S3b's rename merges, every non-migrated repo loses its v1 process.** The v2 skills
   refuse without `.house/`, so those repos have *no* house skill at all until they run `house init`.
   That consequence must be stated in the spec and, ideally, softened — the cheapest softener is a
   clear refusal message in the v2 skills' preflight that says "this repo is not kernel-tracked; run
   `house init`, or see `<archive path>` for the retired v1 process."

**Required cutover choreography** (all four, in order, in one sitting):

1. Merge the rename + archive.
2. Run `./install.sh` (with the new prune step).
3. Verify `ls -la ~/.claude/skills/` — no dangling links, `house-{shaper,orchestrator,builder}` point
   at the v2 dirs, no `house2-*` entries.
4. `/reload-skills` (or restart) in **every open session**, not just the one doing the merge.

Symlink-install makes step 2 mostly a no-op for content (`git pull` is live), but **not** for the
*names* — a rename changes the link set, so `install.sh` is mandatory here in a way it is not for an
ordinary content change. Say so in the spec; it is the kind of step that gets skipped precisely
because symlink installs usually don't need it.

## 5. The cutover precondition — and three sequencing options

### 5a. What the sources literally say

**ADR-0004** (Decision §1):

> The rename to canonical names + v1 archival happen at S3 cutover, after the proving pair (this repo +
> edge-scanner) has been **migrated** and the v2 loop has driven real work end-to-end.

Two conjuncts: *proving pair migrated* AND *the v2 loop has driven real work end-to-end*. The second
is **not scoped per-repo** — "the v2 loop", singular.

**roadmap.md S3b row** is stricter and explicit:

> owns the `house2-*` → canonical rename and the v1 skill archive **once both repos have driven real
> work through v2 end-to-end**

So the roadmap adds a per-repo bar the ADR does not state. Where they disagree, note the S2 precedent
in ADR-0004 itself: *the shipped artifact beats the prose* (`slice.shipped` beat `slice.merged`). Here
neither is "shipped code", so the honest move is to **make the call explicitly in S3b's spec and
reconcile the roadmap line to match** — do not let the two readings coexist into a fourth slice.

**Where the bar stands today:**
- sdlc-skills: **met, twice over.** `[0002]` (patch tier) and `[0003]` (slice tier) both ran the full
  v2 arc — shape → spec_review → plan_check → build → merge_gate → live_check → shipped, with retros.
- edge-scanner: **not migrated, not started.** And per §0, it has no future work — so the strict
  roadmap reading is *unsatisfiable by feature work* and can only be satisfied by adopting the
  ADR-0006 branch.

### 5b. Option (a) — migrate edge-scanner + rename, one slice

Adopt edge-scanner (init + marker wrap), mint the ADR-0006 decision slice, drive it to `shipped`
through `house2-shaper` (mint/record ADR → `adr_review` gate → roadmap+dev-state reconcile → land the
worktree branch), **then** rename + archive.

- **vs. ADR-0004:** fully satisfied under either reading. edge-scanner is migrated *and* drives real
  work end-to-end — a decision-tier arc is a first-class kernel path (`kinds`/`tiers` both include
  `decision`; sdlc-skills ran exactly this shape for the ADR-0001 erratum in `[0003]`).
- **Risk:** medium. Cross-repo work in one slice; the decision-tier v2 run has never been exercised in
  a repo other than sdlc-skills, so it is the first real portability test — which is *good* (it is the
  point of a proving pair) but means unknowns surface mid-slice. Rename choreography then rides on top.
  Recovery if the edge-scanner arc stalls: park the rename, ship migration only — i.e. option (b) is
  the fallback, which makes (a) low-regret.
- **Appetite:** tight but plausible at 2 sessions — **only if `docs/process.*` is explicitly a No-Go**
  (§6). Roughly: 0.6 session adoption + decision arc, 0.5 rename sweep + install.sh prune, 0.5 archive
  + README, 0.4 gates/reconcile/cutover verification.
- **Honesty check:** is landing a 4-file docs-only ADR really "real work driven through v2
  end-to-end"? Yes — but only if it is run as a genuine arc (real `adr_review` gate, real reconcile,
  real `slice.shipped`), not staged to tick a box. If it gets performed rather than run, the
  precondition was faked and the ADR's intent defeated. **Say this in the spec's stakes line.**

### 5c. Option (b) — migrate only; park the rename

S3b = adoption of both repos + `house adopt` docs. Rename and archive move to a later S3c, gated on
edge-scanner shipping something.

- **vs. ADR-0004:** permitted (the ADR sets a floor, not a deadline) but it **defers the defect**.
  ADR-0004: "a `house2-*` name surviving past S3 is a defect, not a convention." Splitting S3 into
  S3a/S3b/S3c and pushing the rename to S3c stretches "past S3" to breaking point.
- **Risk:** low in-slice, **high in program terms** — the trigger for S3c is "edge-scanner ships
  something", and per §0 **edge-scanner will never ship anything again**. This option parks the rename
  behind a condition that cannot occur. That is the fatal objection unless the S3c trigger is
  rewritten to something achievable.
- **Appetite:** comfortably under 2 sessions (~1). Leaves ~1 session of the appetite unspent, which
  argues it is the wrong shape.

### 5d. Option (c) — rename now; edge-scanner migration as a follow-up

Trust sdlc-skills' two shipped v2 slices as sufficient proof; do the rename + archive in S3b; migrate
edge-scanner later.

- **vs. ADR-0004:** **violates the literal text.** The ADR conditions the rename on the *proving pair*
  being migrated, and names edge-scanner. Choosing this means either recording an ADR-0004 erratum
  (the S2 precedent for exactly this move exists and is clean) or amending ADR-0004. Doing it silently
  is not available.
- **Risk:** the specific risk ADR-0004 was written to prevent — the rename lands with the portability
  question unanswered. Everything v2 knows about working in a repo is knowledge of *this* repo, which
  is also the repo where the kernel lives. A `.house/` layout that quietly assumes sdlc-skills would
  be discovered *after* the cutover, when the v1 fallback is archived. Genuinely the worst-ordered
  option.
- **Appetite:** ~1–1.25 sessions. Cheapest, and the cheapness is bought by skipping the test.

### 5e. Recommendation

**(a), with (b) as the in-slice fallback and an explicit escape hatch.** It is the only option that
satisfies both readings of the precondition, it is the only one that answers the portability question
before the v1 fallback disappears, and it fits 2 sessions if — and only if — the `docs/process.*`
rewrite is fenced out.

Structure it so the rename is the *last* unit. If edge-scanner's adoption arc overruns, the slice
finishes at migration-complete and the rename is re-shaped, having lost nothing.

If instead the owner judges the ADR-0006 branch too thin to count as "real work end-to-end", then the
honest path is **(c) with a recorded ADR-0004 erratum** — not (b), because (b)'s trigger can never
fire. The one option to refuse is (b) as written.
